# AI Usage Log

**Tool:** Claude Code (Anthropic) did the implementation, working under written rules: one logical change per commit, one-line commit messages, tests against a real database, and review of every change before it was committed.

This log records decisions where an approach was accepted, changed or rejected. The "Suggestion" column is the approach that was on the table. For a few entries it came from the written brief, from review, or from a deliberate experiment rather than from the assistant's own proposal; the "Why" column says what actually happened and what showed it. Dates and commits point at the change where the decision landed.

| When | Tool | Suggestion | Accepted / Changed / Rejected | Why |

| 2026-09-29, `17317fc` | Claude Code | Use a bigint identity as the primary key of `status_events` (every other table uses a uuid) | Accepted | Status events written in one transaction all get the same `created_at`, so the timestamp cannot order them. A steadily increasing id gives a strict event order. |
| 2026-09-29, `169ce28` | Claude Code | Add a partial unique index so a vehicle can have only one active ride (`OPEN`, `DRIVER_ARRIVED` or `STARTED`). The assistant flagged it as missing from the spec. | Accepted | It keeps "one active ride per vehicle" true even when accepts race each other. A violation (Postgres error 23505) is mapped to `409 VEHICLE_HAS_ACTIVE_RIDE`, and a test triggers it with a real duplicate insert. |
| 2026-09-29, `0141076` | Claude Code | On login, compare the password against a dummy bcrypt hash when the email is unknown | Accepted | Without it an unknown email is answered faster than a wrong password, which shows which emails have accounts. Now both paths do one bcrypt compare and return the same `401 INVALID_CREDENTIALS`. There is no timing test; this is by construction. |
| 2026-09-30, `3cdff5a` | Claude Code | Fix the offline/accept race by locking the driver's row only inside `accept` | Changed | The race test (accept against offline, 20 rounds) failed 6 of 6 runs with "accept 200, offline 200", a driver offline with an active ride. Going offline was a single `UPDATE` whose `NOT EXISTS (active ride)` check used a snapshot taken before it waited for the lock, so it saw no ride. Fix: offline also takes the user row lock in its own first statement and checks in a new one. It passed 10 of 10 runs (200 rounds). |
| 2026-09-30, `736acf5`, `3960600` | Claude Code | Trust one proxy hop (`TRUST_PROXY=1`) so rate limits key on the client IP that Next forwards | Changed | I checked Next's proxy source and what the API really receives: the `/api` rewrite only sets `x-forwarded-host`, never `X-Forwarded-For`, and passes a client-sent one through untouched. Trusting one hop would not have separated users, and would have let anyone forge an IP to get a fresh budget on every request. So `TRUST_PROXY` defaults to false, login limits are keyed by client IP plus account (signup by IP), and only failed logins count. Each has a test. |
| 2026-09-30, `7d54081` | Claude Code | Claim seats with a read, then a write (check the free seats, then update to the computed value) | Rejected | Tried on purpose, temporarily, to check that the last-seat race test can actually fail (with a 15 ms pause between the read and the write to widen the window). Nusrat and Shirin asking for the last seat at once were both matched, which is overbooking, and the test failed 4 of 4 runs. The single conditional `UPDATE` (`seats_occupied + n <= capacity`) stays, with the `CHECK` constraint as a second line of defence. |
